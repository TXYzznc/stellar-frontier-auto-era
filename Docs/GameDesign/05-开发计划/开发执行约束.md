# 开发执行约束

生效日期：2026-08-13

## 第一版开发任务表所有权

- `第一版开发任务表.xlsx` 是第一版任务顺序、依赖、里程碑、工时区间和状态的用户维护来源。
- 只有用户本人可以修改该工作簿。AI、Agent、SKILL、脚本和自动化工具始终只有只读权限，不得因用户授权开发、文档维护或其他项目工作而取得写入权限。
- AI不得直接或间接编辑、覆盖、另存后替换、重算后回写该工作簿，也不得修改其中的状态、实际工时、依赖和备注。
- 开发过程产生的状态、工时、依赖或备注调整只能作为建议列出，由用户决定是否手动更新原工作簿。
- 禁止创建并行的权威副本；任务ID、顺序、依赖、阶段验收门和状态始终以用户维护的原工作簿为准。

## 与 OpenSpec 的职责边界

- 开发任务表决定任务顺序、前置依赖和阶段验收门。
- `Docs/GameDesign/` 提供产品与系统设计依据。
- OpenSpec 负责单个或一组相关开发任务的需求、方案、可测试场景和实现任务分解。
- 代码、数据、资源与测试负责实现和验证；不得反向覆盖开发任务表。

## OpenSpec 分组与命名规范

- 一个 OpenSpec 原则上对应开发任务表中的 2～5 个任务，由AI根据任务目标、依赖关系、实现内聚性和可验收边界自行决定具体数量；不得机械地一项任务建立一个 OpenSpec，也不得把整张任务表一次性纳入同一个 OpenSpec。
- 同一个 OpenSpec 内的任务必须目标一致、依赖连续，并能形成共同的设计与验收边界；即使任务属于同一模块，也不得跨越阶段验收门组合。
- OpenSpec change ID 同时作为目录名和文档中的变更名称，必须使用OpenSpec CLI兼容的英文`kebab-case`：仅使用小写英文字母、数字和连字符，不使用中文、空格或下划线。
- OpenSpec change ID 必须包含以字母`b`开头的管理批次号、对应任务编号和简短英文任务概要。批次号格式为`b<两位序号>`，用于满足OpenSpec CLI“名称必须以字母开头”的校验；任务编号允许简写并转为小写，但必须能够无歧义地映射回`第一版开发任务表.xlsx`中的原始任务ID。
- 非并行 OpenSpec 命名格式：`b<两位序号>-<任务编号范围或组合>-<英文任务概要>`，例如：`b01-p01-p03-engineering-baseline`。
- 同一执行批次存在并行 OpenSpec 时，共用相同的管理批次号，并在批次号后标记`parallel`和并行领域；命名格式为：`b<两位序号>-parallel-<领域>-<任务编号范围或组合>-<英文任务概要>`。
- 程序与美术并行示例：`b01-parallel-program-p01-p03-engineering-baseline`、`b01-parallel-art-art01-art02-visual-rnd`。其中相同的`b01`表示二者属于同一执行批次，不表示两个 OpenSpec 是同一个变更。
- 管理批次号按执行批次递增，而不是按 OpenSpec 文件夹数量递增；同批并行项复用批次号，下一批使用下一个序号。
- 建立 OpenSpec 前必须对照任务表核验原始任务ID、前置依赖和阶段验收门；OpenSpec 的 proposal、design、specs 与 tasks 必须明确列出其覆盖的原始任务ID，名称中的简写不得替代正文中的完整ID。
- 后续所有 OpenSpec 的规划、创建、实施、验证与归档都必须遵守本节；若实际开发发现任务分组需要调整，只能调整 OpenSpec 边界或向用户建议修改任务表，不得由AI擅自修改任务表。

## OpenSpec 方案确认门禁

- 开发任务表和`Docs/GameDesign/`确认的是需求、范围、顺序与验收依据，不代表具体实现方式、技术架构或美术生产方案已经获得确认。
- 每个OpenSpec在创建或填写artifact前，必须先与用户讨论该变更的实现方式和大方向设计；不得把需求已确认推定为实现方案已确认。
- 必须讨论并取得用户确认的内容包括：模块与程序集边界、数据模型、公共接口、生命周期、依赖关系、资源结构、序列化与存档语义、异步与取消、性能约束，以及会影响后续工作的工具或生产流程。
- 局部代码写法、私有成员命名、等价重构和不改变已确认契约的机械实现细节可由AI自行决定，但仍须遵守项目约定和对应OpenSpec。
- 讨论完成后，AI必须先提交该OpenSpec的决策摘要，至少包含目标、选择的方案、明确边界、验收方式和约束。只有用户明确确认该OpenSpec的决策摘要后，AI才可以创建或填写proposal、design、specs和tasks。
- 并行OpenSpec分别执行方案确认门禁。程序OpenSpec的确认不能替代美术OpenSpec的确认，反之亦然；同一批次编号不构成共享授权。
- 实施中若发现需要改变已确认的架构或实现契约，必须暂停相关实现，重新与用户讨论并取得确认，再更新OpenSpec；不得先实现后补写方案。

## 方案讨论增量归档

- 连续方案讨论每累计两轮，必须至少完成一次增量归档；重大边界、不可逆选择、跨项目契约或会影响后续任务的结论确认后立即归档，不等待整组讨论结束。
- 增量归档写入[方案讨论增量归档](../90-设计管理/方案讨论增量归档.md)，只保存已确认决策检查点、明确排除、待决事项和受影响任务，不保存原始聊天流水。
- 稳定结论还必须同步到对应系统文档与决策记录，当前完成度同步到设计状态总表，未决事项同步到开放问题与讨论顺序。
- 增量归档不等于OpenSpec最终决策摘要，也不构成artifact创建授权；创建proposal、design、specs和tasks前仍须提交完整决策摘要并取得用户明确确认。

## 美术独立项目与持续集成

- 正式美术可以在独立Unity美术项目中并行制作，但必须与主工程使用一致的Unity、URP、单位、坐标、材质、Shader、动画和资源交付合同。
- `ART-G0`通过前必须完成代表性资源贯通验证；不得仅凭文档合同直接开始全量资源生产。
- 场景、机器组件、建筑资源点、动画VFX和UI资源按领域完成后立即分批导入，不等待`ART-G1`全部资源完成。
- `ART-G1`表示独立美术项目的全部正式资源通过专业验收；`ART-G2`表示资源已在主工程完成绑定、性能和一致性验收。
- 程序灰盒不等待正式美术，但第一版最终验收`G8`必须依赖`ART-G2`。
