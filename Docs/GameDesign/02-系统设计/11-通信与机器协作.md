# 通信与机器协作系统

> 状态：后续版本核心规则已确认；第一版只实现通信组件管理与探索能力检查，不运行真实通信  
> 关联文档：[机器、自动化与算法](01-机器自动化与算法.md)｜[区域探索与拓荒](02-区域探索与拓荒.md)｜[能源、储存与物流](06-能源储存与物流.md)

## 系统目的

通信系统让机器能够取得自身传感器原本无法获取的信息，并在不依赖中枢的情况下进行本地协作。它服务于机器组装、节点算法、任务调度与故障诊断，不扩展为铺设网络、配置频段或维护复杂拓扑的独立基建玩法。

通信需要同时支持三种关系：

- 机器读取附近建筑物、资源点或机器公开状态。
- 已连接机器向中枢上传信息，中枢算法据此调度机器。
- 机器通过有限距离通信发布请求，由附近机器自主响应。

## 第一版实现边界

- 第一版实现通信接收器和发射器的制造、入库、安装、拆卸、升级、槽位占用、能耗、属性显示与能力标签。
- 探索机器准备检查要求同时安装、通电并正常启用接收器和发射器；通过后显示“远程通信能力就绪”。
- 第一版不运行机器间请求广播、请求记录、能力硬筛选、响应算法、中枢远程调用、通信距离、信号覆盖、断连和动态运输。
- 第一版不提供运输请求响应模板。本文其余通信请求与机器协作规则作为后续版本的正式设计保留，不属于第一版开发和验收。
- 通信接收器持续监听的5点算力只在真实通信玩法启用后生效。第一版仅在执行探索机器通信能力自检时产生短暂计算需求，不因安装一个暂不可用的组件而持续占用算力。

## 对象公开状态的读取

- 玩家在现场与建筑物或资源点交互时，可以直接查看该对象的公开状态，不需要传感器。
- 建筑物和资源点不安装传感器、计算核心或效应器，也不直接连接中枢或主动发射通信信号。
- 机器必须安装**对象状态传感器**，才能在算法中读取附近建筑物、资源点或其他允许读取对象的公开状态。
- 对象状态传感器具有物理读取范围、有限目标通道和更新频率。玩家将每个通道明确绑定到范围内的一个对象，不会自动读取整块区域的所有对象。
- 目标离开范围、被摧毁或无法读取时，输出进入无效或过期状态；目标重新满足条件后自动恢复。
- 第一版不处理视线遮挡、材质衰减或随机读取失败。
- 对象公开状态只包括对象自身明确暴露的数据。土壤湿度、环境温度、敌人位置等外部或隐藏状态，仍需要相应的专用传感器。
- 现场面板还可以向玩家显示生长速度、生产效率和批次结果等综合结果反馈，但这些玩家反馈不因此成为对象公开接口，也不生成第一版对象状态传感器端口。
- 有效的专用传感器读数可以显示在现场面板的“关联传感数据”区域；没有对应传感数据时不显示该隐藏状态字段。

公开状态示例：

- 仓库：库存、容量、剩余空间。
- 工厂：输入缓存、输出缓存、生产进度、运行状态和阻塞原因。
- 资源点：生产模型、阶段、进度、可作业数量、剩余储量、产出缓存及该生产模型明确公开的状态。

## 通信组件与连接边界

- **通信接收器**占用传感器槽位，使机器能够接收通信范围内的机器请求。
- **通信发射器**占用效应器槽位，使机器能够发布请求及同一请求的更新或关闭状态。
- 在已经拓荒并由信号塔连接的区域，符合条件的机器自动连接中枢。机器传感器的选定输出可以通过该连接上传，不额外要求安装通信发射器。
- 中枢算法可以读取已经上传的传感器数据，并向已连接机器提交包含兼容效应器行为的远程机器任务；远程任务仍需经过目标机器的任务队列、优先级和效应器安全仲裁。
- 正在拓荒的区域中，普通机器无法连接中枢，只能运行本地算法并使用本地通信协作。
- 远程探索机器若要在未接入区域获得完整中枢连接，必须同时安装通信接收器和通信发射器，分别付出一个传感器槽位和一个效应器槽位。
- 机器间本地通信的有效距离由发射距离与接收距离共同限制。第一版不处理视线遮挡、信号衰减、随机丢包、自动中继和多跳网络。

机器连接中枢后自动上传名称、型号、区域、分组、运行、损坏、算力、队列和位置等基础遥测；传感器获取的世界数据只有被明确设置为发布到中枢后，才能进入中枢算法。远程任务成功送达后不会因断连自动取消，结果在本地暂存并于重连后上传；未送达任务因断连失败，不自动重试。

## 请求广播模型

请求是发送机器在一定时间内持续维护的一项公开需求，不是指定接收者的直接命令。

- 通信距离内所有安装并启动通信接收器的机器都能接收到请求。
- 玩家不需要配置订阅槽位、信号协议或来源过滤。
- 接收机器根据请求的能力要求和自身当前能力进行确定性硬筛选。不满足要求的请求不会进入任务候选队列。
- 发送者不需要知道由哪台机器处理；接收者也不需要向发送者预先注册。
- 同一个请求始终使用同一个请求ID。重复广播、内容变化和需求结束只更新本地已有记录，不产生多个重复任务。

一条请求至少包含：

- 请求ID与当前版本。
- 请求来源及任务对象。
- 请求类型与任务参数。
- 剩余需求量或结束条件。
- 完成任务所需的能力标签集合。
- 基础优先级。
- 当前状态：进行中或已结束。

### 运输请求的来源与目的地

- 第一版运输请求必须明确包含来源对象、取货端点、目的地对象、交付端点和物品类型，不使用“任意兼容仓库”等动态目的地。
- 发布请求的监控机通过对象状态传感器绑定资源点；来源对象、取货端点、资源类型和缓存数量由传感器的公开端口连入“发布／维护运输请求”节点，不由系统隐藏推断。
- 目的地由玩家在发送机算法中使用对象引用节点明确绑定。可选择已知且具有兼容收货端点的仓库、生产设施或其他对象。
- 对象引用只保存对象身份与公开端点，不代表发送机能够读取目的地的实时库存。目的地容量需要通过额外传感器与通信取得，或由运输机器抵达后根据资源转移结果判断。
- “发布／维护运输请求”是有状态节点：条件首次成立时创建新请求ID；条件持续成立时更新同一请求的数量和版本；条件失效或需求归零时关闭请求；之后再次产生需求时创建新的请求ID。
- 第一版由发送方把请求描述成“从哪里取、取什么、取多少、送到哪里”的完整工作。由运输机器或中枢动态选择目的地属于后续高级算法范围。

## 能力筛选

请求只描述完成工作所需的能力，不绑定具体机器型号或效应器名称。

- 能力标签可以由机器载体、移动结构、货舱、传感器和效应器共同提供。
- 不同组件可以提供相同或兼容的能力标签。例如机械臂和其他装卸装置都可以提供资源转移能力。
- 系统根据机器当前实际可用的能力判断是否兼容，同时检查损坏、休眠、可用货舱空间等必要运行条件。
- 能力筛选只决定请求能否进入候选任务队列，不代表机器已经执行，也不会预占请求需求量。

例如，一条自主运输请求可以同时要求移动、资源装载和资源转移能力，而不会规定必须安装某个具体型号的机械臂。

## 任务与效应器队列

请求、机器任务和效应器动作分为三个层级：

1. **请求记录**保存发送方当前公开的需求状态。
2. **机器任务队列**保存由本地算法、中枢算法或通信请求产生的完整任务，并按优先级调度。玩家的开机、休眠、配置等管理操作不生成世界作业任务。
3. **效应器执行队列**保存完整任务拆分出的具体动作；每个效应器拥有一个等待队列和一个当前动作。

机器自身任务与外部请求派生任务使用最低、低、普通、高、紧急五档任务优先级。优先级相同时按照进入队列的时间处理。不同任务若不争夺同一个效应器、移动结构、货舱空间或其他共享执行资源，可以并行执行。系统不自动提高长期等待任务的优先级，任务饥饿需要由玩家通过算法和诊断处理。

一项完整任务不能因为涉及多个效应器而被复制成数个互不相关的任务。系统保留一个父任务，并为参与执行的效应器建立关联动作；取消、完成和异常均通过同一任务ID汇总。

所有世界行为都必须属于机器任务。没有显式任务上下文的行为节点在首次产生世界行为时自动创建单行为任务；行为结果事件直接连接的后续动作继承同一任务ID。独立传感器采样、周期计时器新周期和其他根触发默认创建新任务，不会因来源或目标相同而自动合并。

玩家可以使用“提交机器任务”节点，在第一个动作前设置任务名称、目标和优先级，并让多个并行效应器动作共享父任务。系统只维护上下文、调度和记录，不替玩家增加防重、恢复或重试逻辑。

机器任务生命周期包含排队中、执行中、暂停、取消中、已完成、已失败和已取消。等待算力、效应器、移动结构、货舱、资源、目标、连接或供电等内容作为可并存的等待原因记录，不扩展成大量互斥任务状态。通信请求关闭只删除尚未开始的相关任务；已经进入执行阶段的任务仍按既有请求关闭和有效贡献规则处理。

第一版单台机器最多等待32个任务，单个效应器最多等待16个行为，单个通信接收器最多保存64条有效请求记录。满队列拒绝新内容并返回明确原因，不覆盖旧内容或按优先级驱逐；通信与任务来源可以根据拒绝结果自行重试。

任务调度与算力调度是两个系统：任务调度决定机器准备做什么，算力策略决定传感器、算法节点和效应器请求何时获得算力。

### 请求记录转化为机器任务

- 通信接收器自动接收范围内的广播，系统先按能力标签进行确定性硬筛选，并把兼容内容保存为请求记录；请求记录本身不等于机器任务，也不会直接驱动机器行动。
- 机器必须运行相应的请求处理算法，才能读取兼容请求记录并提交机器任务。没有处理算法时，请求仍可查看和诊断，但机器不会响应。
- 算法库提供运输请求响应模板，使玩家无需逐个订阅发送者；玩家可以修改模板，按请求类型、优先级、本机状态或其他可用信息决定是否响应。
- 默认模板在收到或更新运输请求时，检查本机是否已有相同请求ID的未结束响应任务。没有时才提交任务，并默认继承请求优先级。
- 重复广播由系统合并为同一请求记录；同一请求的任务防重由模板中的可见节点完成，不属于系统隐藏规则。玩家可以删除或修改该逻辑。
- 运输任务轮到执行及抵达来源时都必须重新验证请求状态、来源库存与本机容量。机器出发不预占需求，实际取得资源才形成有效贡献。

### 运输响应与独立交付责任

- 实际取得资源以前，响应任务持续依赖原请求。请求关闭时，排队或前往来源的任务取消；正在执行可中断转移时在最近整数单位结算后停止。
- 机器实际取得资源后，已产生有效贡献，并将剩余流程转化为“交付所携资源”的独立任务；该任务不再因原请求关闭或后续优先级变化而取消。
- 独立交付任务默认继承原响应任务的优先级。玩家可以通过算法提高交付优先级，但不能无处理地丢弃已经形成的后续责任。
- 交付失败时资源继续保留在机器货舱，任务进入相应失败或等待状态并产生明确警告；系统不会删除资源、瞬移入库或擅自选择其他仓库。

### 异常后的算法干预与未解决责任

- 玩家不能绕过算法直接命令机器移动、装卸或改变货舱内容；异常干预通过修改算法结构、运行参数或对象绑定并点击“应用”完成。
- 节点配置在安全点应用并重启后，新算法自动收到“算法启动／重新应用”事件，立即重新读取货舱、任务和未解决责任，不要求玩家额外制造触发事件。
- 机器独立保存未解决责任，至少包含责任类型、携带物品与数量、原始来源、原目的地、原请求ID、形成原因和最近失败原因。算法替换、机器重启、断电和读档均不清除责任。
- 货物成功交付、退回来源或经算法转移到其他合法位置后，对应责任才会解除。系统只保存因果与状态，不替玩家决定备用目的地或处置方式。
- 基础运输模板对实体物品目的地暂时容量不足提供可见的“等待后重试”路径；目的地永久失效时停止重复尝试、保留货物并报警，等待玩家修改目的地或恢复算法。
- 木材、矿石、水和生物质进入兼容仓库后立即结算为全局通用资源，不占仓库实体容量，不会触发“仓库容量不足”。该异常只适用于需要实体储存的物品。

## 有效贡献与需求量结算

每一种请求必须定义什么结果属于**有效贡献**。只有有效贡献实际发生时，才减少请求的剩余需求量。

- 接收请求、进入队列、前往目标、瞄准或准备工具均不构成有效贡献。
- 机器出发时不预占需求量，也不为预计产出建立认领份额。
- 多台机器可以同时响应同一请求；先实际产生的有效贡献先结算。
- 需求量归零或请求条件不再成立时，发送方以原请求ID发布“已结束”更新。
- 因为没有出发预占，可能出现额外机器已经在路上、但最终没有剩余工作可做的情况。这是通信距离与调度效率产生实际价值的允许结果。

有效贡献示例：

- 运输：机器实际从来源取走资源。
- 维修：目标实际恢复结构完整度。
- 浇水：目标实际获得水分。
- 补给：目标实际收到物资。
- 建造：实际增加建造进度。

具体战斗、救援等请求的有效贡献定义，随对应系统细化。

## 请求关闭与通用取消语义

请求关闭只能取消仍依赖该请求的工作，不能撤销已经产生的结果，也不能抹除由结果产生的后续责任。

| 机器所处阶段 | 通用定义 | 收到请求关闭后的处理 |
|---|---|---|
| 候选或排队 | 尚未执行相关动作 | 直接移除任务 |
| 准备或前往 | 已开始响应，但尚未作用于任务对象 | 取消后续动作并重新调度 |
| 可安全中断的执行 | 正在执行且可以安全停止 | 在最近安全点停止 |
| 不可安全中断的原子动作 | 当前最小动作不能安全停止 | 完成当前原子动作后重新判断 |
| 已产生有效贡献 | 已经实际减少请求需求 | 保留已经产生的结果 |
| 已产生后续责任 | 已获得对象或形成必须处理的状态 | 转化为独立任务并继续完成 |
| 已完成 | 相关工作已经结束 | 不受影响 |

不可安全中断只保护当前最小原子动作，不保护整个任务。原子动作结束后，系统依次判断是否产生有效贡献、是否生成后续责任，以及是否还需要继续执行。

## 后续责任

**后续责任**是机器产生有效贡献后，因为已经取得对象或改变状态而必须完成的收尾工作。后续责任脱离原请求，作为机器自身的独立任务继续存在。

- 从资源点取走资源后，形成把所携资源送往目的地的后续责任。
- 搭载待救援对象后，形成将对象送往安全地点的后续责任。
- 取走废弃物后，形成将其送往处理位置的后续责任。
- 一次浇水或维修通常不产生后续责任。
- 已经发射的弹丸不能收回，但只完成当前不可中断动作，不自动形成持续任务。

通用原则为：未产生结果的工作尽量取消；不能安全中断的动作只完成当前最小单元；已经产生的结果予以保留；由结果产生的责任必须继续处理。

## 通信范围外的状态更新

- 请求更新和关闭仍受本地通信距离限制，不会全局瞬时送达。
- 已经离开发射范围的响应机器可能无法立即收到关闭更新，因此可能继续前往任务来源。
- 机器抵达并准备作用于任务对象前必须再次验证请求和对象状态；需求已经结束时不产生贡献，并重新调度。
- 中枢不会默认充当所有本地请求的全局转发器，以免绕过未拓荒区域与本地通信的边界。

## 示例：矿石运输请求

```text
矿山监控机读取矿山缓存：50单位矿石待运
→ 发布运输请求R-1024，剩余需求50
→ 范围内兼容货运机A、B、C将任务加入各自队列
→ A实际取走30，R-1024更新为剩余20
→ A生成独立的“交付所携矿石”任务
→ B实际取走20，R-1024更新为剩余0并关闭
→ B生成独立交付任务
→ C若收到关闭更新且尚未取货，则取消响应
→ A、B继续交付，不受R-1024关闭影响
```

## 玩家反馈要求

- 机器界面应区分收到的请求、排队任务、当前任务和效应器当前动作。
- 请求需要显示来源、要求能力、剩余需求、优先级、有效性和关闭原因。
- 被能力筛选拒绝的请求默认不占据玩家注意力；调试界面可以说明缺少的能力。
- 请求关闭、任务取消、安全点等待、能力不足和目标失效必须留下可诊断记录。
- 同一请求的传播、更新、有效贡献和后续责任应能通过请求ID追踪。
