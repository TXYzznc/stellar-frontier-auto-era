# 长期窗口持久任务队列

## 外部阻塞必须让出执行位（2026-09-10 用户明确要求）

- Active表示正在执行的独立工作单元，不是整个OpenSpec占位。仅一部分缺决定时先继续同任务其它安全工作；若仍有独立后续任务可做，将真正待外部输入的剩余工作挂起，不让后续任务堵塞。
- 确实无法继续当前单元时，保存检查点、释放不必要工具占用，记录原因和恢复条件，执行 `block --role <role> --task-id <id> --reason <原因> --checkpoint <现场> --resume-when <解除条件> --claim-next`。阻塞任务仍在suspended列表中但state=blocked，不是完成；claim/complete自动跳过它。
- 收到决定/依赖证据后执行 `unblock --role <role> --task-id <id> --evidence <实际依据> --claim-next`。解除后可恢复，但不抢占正在执行的新Active。不能仅因时间过去或收到普通通知解除阻塞。
- 不得把本可继续的工作假称外部阻塞。完整批次可拆成可执行单元与真实等待项；未完成范围不可因让位而丢失或勾选完成。发起人收到依赖请求应处理，不以挂起来替代解决问题。
- 该规则覆盖历史“等待也占Active”口径；既有合法抢占仍用preempt，未解决依赖的挂起不再自动抢回执行位。角色在安全检查点读取本节，不用普通广播打断正在运行的窗口。

## 自治恢复、协作与制作人升级（2026-09-12 用户明确要求）

窗口在已授权范围内自行决定重试、日志检查、替代工具和局部修复；只有窗口判断自己确实无法完成时才升级。已知目标角色时直接点对点申请协作并登记队列；目标不明、失联或需要查询租约／端口时交给任务调度窗口路由。协作请求发送后，发起窗口继续其它安全工作。

仅在需要方向取舍、范围／优先级／负责人变化、新授权、无法解除的合同冲突或所有可行协作均失败时通知制作人。只有全部验收标准和实际证据齐全时才登记 `result-ready` 供制作人验收；中间验证失败、截图空白、引用未显示或工具超时均属于窗口自助处理范围，不得提前通知制作人或进入 `AwaitingProducerAcceptance`。窗口不得自行 `Accepted`。

## 完成必须实际回传制作人（2026-09-10 用户明确要求）

每个角色完成一个已派发任务时，必须通过窗口消息接口向制作人实际发送一次完成回传，
含任务ID、交付/验证证据、未覆盖项、占用释放情况及下一队列状态；不能仅在自己窗口写“已完成/请制作人验收”。
涉及视觉效果的验收，回传必须包含实际落盘并可查看的截图，且应直接附在对话中供制作人查看；截图必须展示批准的真实美术素材，纯色块、脚本线框或占位图不构成视觉验收证据。仅有截图接口元数据、文件路径或文字描述也不构成视觉验收证据。
该规则覆盖历史“普通独立任务完成不通知制作人”的口径，不要求每个中间步骤汇报。
回传与执行解耦：发送后按队列继续已授权下一任务，不等待“已阅”；仅真实决策/依赖阻塞才等待。
接口发送失败时保留未送达状态并在安全节点重试，不声称已经通知；不阻塞可独立继续的工作。

本协议解决“向运行中窗口下发新任务会立刻打断当前工作”的问题。窗口消息不再承担普通任务排队；
正式派发来源仍是派发单、OpenSpec和专业文档，队列只保存本机执行顺序和恢复状态。

## 每次回复开头的任务概览（2026-09-09 用户要求）

所有角色（含制作人、程序、美术、测试、快速执行与手动触发的Git集成）每次对用户回复时，
必须先简短列出本角色当前全部未完成任务及执行顺序，再写正文；进度回复和最终回复均适用。
这是当前窗口的任务清单，不要求每次扫描其它角色或重复整个项目任务表。

- `处理中`：Active 的任务简称及当前步骤；Active 因外部依赖无法推进时明确标为阻塞，不伪称运行。
- `待处理／挂起`：列出未完成的待决定、待验收、待依赖及 Suspended 任务，并用短语注明原因。
- `排队`：逐项列出全部 Pending，不以“还有N项”省略名称。编号按实际执行顺序：当前任务→可恢复的
  Suspended（遵循工具恢复次序）→Pending（优先级数字升序、同级FIFO）。尚不能确定顺序的外部阻塞项注明条件，不编造顺位。
- 队列之外本轮用户刚提出、尚未入队的任务也必须体现；不得因队列为空遗漏实际工作，亦不得把未授权设想当任务。
- 无任务的类别写“无”；已完成／取消的历史任务不反复列入，必要时只在正文报告本轮完成结果。
- 首次回复／上下文恢复／状态变更后以本机队列、派发依据与最新用户指示核对；同一回合无变化可复用
  已核实快照，避免为每条短进度重复调用工具。无法读取时注明“待核实”，不得猜测。
- 推荐一至三行紧凑表达，例如：`任务顺序：①处理中：低模替换；②挂起：UI接入（替换后恢复）；③排队：输入回归。待决定：无。`
- 任务概览不改变授权、优先级或暂停规则，不触发新任务、不要求“已阅”，不能成为结束执行回合的理由。
- 连续逐项讨论中，用户确认当前问题后，应记录结论并主动接续下一项未定问题，不另等“继续”；不重问已确认事项，也不自动启动尚未授权的实施。

## 设计讨论先归类、再讨论差异（2026-09-09 用户要求）

- 提问前先查对象所属类别及现行共用合同，以最新已确认决策核对旧文档，不把残留旧条款作为新方案依据。
- 类别已确定的对象默认继承该类别适用规则。例如水泵归入建筑，其区域供电、停机与恢复等沿用建筑／电网规则；水货物包装与转移沿用通用货物／物流规则，不另建空桶供应链。
- 只讨论对象特有条件、缺失参数、真实冲突与必要例外；不按对象重复确认共用规则，不为了完成讨论轮数制造选择题。
- 产出文档区分“继承依据、特有差异、待定项”；被共用合同覆盖的内容以引用为主。发现更通用的共性时先归纳，不直接增加专用系统。

## 状态文件与工具

- 本机队列：`.ai/dispatch/task-queue.local.json`，被Git忽略，但在项目重启和窗口上下文恢复后保留。
- 管理工具：`python tools/window_task_queue.py`。
- 每个职能独立维护`active`、`pending`、`suspended`和`completed`。
- 结果生命周期：`.ai/dispatch/task-lifecycle.local.json`，由 `python tools/task_lifecycle.py` 维护。
  - `result-ready` 登记待验收，`accept` 制作人验收通过，`rework` 退回返修。
  - `cancel` 用于用户或制作人决定任务不再执行：写成 `Cancelled`，清空验收人并保留取消原因。
    `Cancelled` 属于终态，守护器不得据此唤醒窗口，也不得计入 `completed`。
  - 取消只解除执行义务，不产生完成或验收结论；重新执行必须重新入队并获得新的派发授权。
- 写入采用锁文件与原子替换；禁止人工同时编辑队列JSON。

初始化示例：

```powershell
python tools/window_task_queue.py init --roles producer git-integration rapid-executor art-3d art-concept-3d art-2d client backend design qa
```

## 普通入队不抢占

```powershell
python tools/window_task_queue.py enqueue `
  --role art-concept-3d `
  --task-id b03-g02-axonometric `
  --title "G02轴测效果图" `
  --priority 10 `
  --dispatch-path "openspec/changes/b03-parallel-art-art004-art005-production-rnd/tasks.md"
```

- 一个窗口同时只能有一个`active`任务。
- 新的独立任务永远进入`pending`，即使优先级更高，也不得替换`active`。
- `pending`按数字优先级从小到大排序；同优先级按`enqueuedSeq`执行，未指定优先级默认为50。
- 下发方发现目标窗口正在运行时，只写队列，不调用窗口消息接口发送任务正文。
- 若目标窗口空闲且没有`active`，可`claim`后用一条启动消息唤醒；运行中的窗口不接收普通派发消息。

## 快速执行候选的直接入队

- 原专业窗口是快速执行候选检查和拆包的第一责任人，不等待制作人扫描任务。
- 已冻结的独立工作单元满足`RapidExecution.md`六项门槛时，原窗口直接向`rapid-executor`入队；
  `source`记录原职能或OpenSpec ID，`summary`必须写明允许／禁止范围、自动门禁、完成回传和失败回退。
- 快速执行空闲时才发送启动消息；已有Active时仅入队，不能用消息抢占。
- 原窗口不得把未冻结决策、最终专业验收或整个大型Active任务整体转移给快速执行。
- 派出后原窗口继续当前Active内其它不依赖结果的工作；只有确实依赖快速执行结果时才可等待。

## 窗口领取与收尾

窗口启动、上下文恢复和每项任务完成收尾后必须读取自己的队列：

```powershell
python tools/window_task_queue.py status --role art-concept-3d
python tools/window_task_queue.py claim --role art-concept-3d
python tools/window_task_queue.py complete --role art-concept-3d --task-id b03-g01-axonometric --claim-next
```

完成当前任务必须先保存产物、自验、记录证据、释放不再需要的共享资源并完成规定汇报。使用
`--claim-next`后，工具优先恢复曾被合法抢占的`suspended`任务，再按“优先级＋FIFO”领取下一项。

## 允许抢占的唯一条件

普通新任务、后续对象、优先级变化、普通知悉和制作人希望加速均不得抢占。只有以下情况允许在
安全检查点调用`preempt`：

1. S0／S1问题或资源／数据安全风险，并经用户或制作人明确批准；
2. 用户明确要求“立即切换”；
3. 新信息证明继续当前产物必然作废。

```powershell
python tools/window_task_queue.py preempt `
  --role art-3d `
  --task-id urgent-fix `
  --reason-kind s1 `
  --checkpoint "源文件已保存，Unity与DCC已释放" `
  --approved-by producer
```

抢占必须记录检查点和批准来源。被抢占任务进入`suspended`，紧急任务完成后优先自动恢复。无法形成
安全检查点时不得强制切换。

## 当前任务修订与独立新任务

- 修改当前产物的合同修订：若继续工作会造成确定性返工，可在安全检查点合并到当前任务；这不是
  开始第二项独立任务。
- 与当前产物无关的新对象、新功能或后续阶段：进入`pending`。
- 仅提供将来会用到的参考信息：写入对应派发单／OpenSpec或队列摘要，不直接消息打断窗口。
- 用户直接向运行中窗口提出新任务时，窗口必须先分类；若不是合法抢占，登记到`pending`后继续当前任务。

## 3D前置生产的专用阶段门

三视图与生产说明任务只能在对应主美技术文档经制作人对照归档需求验收通过后入队。主美刚完成
文档不等于允许3D原画开工。验收未通过时，3D原画队列中不得出现该对象的三视图／生产说明任务。
