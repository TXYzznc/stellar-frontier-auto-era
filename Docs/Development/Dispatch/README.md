# 多窗口任务派发

本目录保存OpenSpec建立前的专业窗口探索派发单，以及当前多窗口协作占用情况。它不替代
用户维护的`第一版开发任务表.xlsx`，不构成任务顺序、依赖、工时或完成状态的第二权威来源。

## 目录职责

- `ActiveAssignments.md`：由制作人窗口独占维护，记录当前派发单、专业窗口、协作阶段、
  文件／工具占用和阻塞，不记录任务表意义上的完成状态。
- `DispatchTemplate.md`：方案探索派发单的固定字段、启动检查、修改权限、锁与回传模板。
- `PauseAndRecovery.md`：局部／批次／项目暂停、S0～S2抢占、现场保护和恢复门禁。
- `RoleRouting.md`：工作窗口职责、优先使用的Agent职责／SKILL和项目级专项策划路由。
- `WindowAutomation.md`：固定窗口注册、制作人自动派发、状态监控和失效降级规则。
- `WindowRegistry.example.json`：本机窗口注册表结构示例；实际注册表写入被Git忽略的
  `.ai/dispatch/window-registry.local.json`。
- `Active/<派发ID>.md`：OpenSpec建立前的独立方案探索派发单。派发ID优先使用预定的
  OpenSpec change ID，并遵守批次号、并行领域和任务编号命名规范。
- 专业窗口完成方案讨论、用户确认决策摘要并创建OpenSpec后，派发单移动到
  `openspec/changes/<change-id>/dispatch.md`，随后与该OpenSpec一起归档；本目录不再建立
  独立历史副本。

## 协作状态

| 状态 | 含义 |
|---|---|
| 待领取 | 制作人已生成派发单，尚未交给专业窗口 |
| 方案讨论 | 专业窗口正在检查项目并与用户收敛实现或生产方案 |
| 等待复核 | 专业窗口已提交决策摘要，等待制作人检查跨职能依赖和冲突 |
| 可实施 | 决策摘要与OpenSpec已确认，所需文件和工具占用已授予 |
| 实施中 | 专业窗口正在开发、制作或执行专业验证 |
| 待验收 | 专业窗口已提交结果，等待测试、制作人或用户验收 |
| 暂停 | 因依赖、设计冲突、文件冲突或工具占用而停止推进 |

这些状态只描述窗口协作阶段。任务表中的状态、实际工时和备注始终由用户本人维护。

## 锁与占用规则

- 写权限以业务目录锁为主；场景、Prefab、ProjectSettings、共享配置、`.blend`和其他
  高冲突资产按单文件补充锁定。不得为了省事锁定整个项目，也不得要求逐个登记普通文件。
- 同一目录或高冲突文件在同一时段只能由一个实施窗口写入。只读检查不取得写锁，但
  任何会驱动Unity状态的读取、测试或截图仍须取得对应Unity实例锁。
- Unity、Blender文件和外部绘图工程使用工具独占锁。客户端和测试轮流使用主工程8090；
  美术项目8091及具体DCC源文件也必须登记占用者和释放条件。
- 多窗口共享同一Git工作区时，暂存区和分支状态也是共享资源。暂存或提交前必须取得
  短期Git索引锁；禁止`git add -A`和`git add .`，只能显式暂存派发范围内的路径。
- 未持有Git索引锁的窗口可以在已分配目录内编辑，但不得暂存、提交、变基、合并、切换
  分支或重写历史。提交前必须检查暂存区没有其他窗口或用户内容，提交后立即释放锁。
- 所有窗口的Git提交标题、概要和正文描述必须使用中文；专业术语、文件名、类型名和派发／
  OpenSpec编号可保留原文。不得为满足本规则改写历史提交。
- 专业窗口不得直接修改`ActiveAssignments.md`；它通过交付回传申请变更，由制作人窗口
  统一更新占用和状态，避免总览文件成为并行写冲突点。

## 基本流程

1. 制作人只读核对任务表、设计来源、依赖、阶段门和可并行条件。
2. 制作人生成方案探索派发单并登记到`ActiveAssignments.md`。
3. 制作人优先按`WindowAutomation.md`向已注册专业窗口自动发送派发消息；窗口未注册、
   失效或派发失败时，降级为由用户手动打开对应窗口并发送派发单路径。
4. 专业窗口先检查项目、工具、SKILL和工作流。工作窗口可使用当前环境提供的全部SKILL，
   但应优先使用`RoleRouting.md`列出的职能能力；真正委派的子Agent仍遵守Agent白名单。
5. 专业窗口与用户讨论具体实现或生产方案，并按每累计两轮至少一次的规则增量归档。
6. 专业窗口提交决策摘要；用户确认后才创建和填写OpenSpec artifacts。
7. 制作人复核跨职能依赖、文件冲突和Unity占用后，任务进入实施。
8. 专业窗口提交代码／资源、验证证据、提交号、限制和未决事项，不执行Git推送。
9. 测试窗口默认只诊断和报告；缺陷交回原实现窗口修复。
10. 用户验收后，制作人归档OpenSpec并提供任务表手动更新建议。
