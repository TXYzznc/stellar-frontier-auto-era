# 多窗口任务派发

本目录保存OpenSpec建立前的专业窗口探索派发单，以及当前多窗口协作占用情况。它不替代
用户维护的`第一版开发任务表.xlsx`，不构成任务顺序、依赖、工时或完成状态的第二权威来源。

## 目录职责

- `ActiveAssignments.md`：由制作人窗口维护批次级派发、异常和长期占用，不再登记普通进度、
  每次Unity交接或Git提交；不记录任务表意义上的完成状态。
- `DispatchTemplate.md`：方案探索派发单的固定字段、启动检查、修改权限、锁与回传模板。
- `PauseAndRecovery.md`：局部／批次／项目暂停、S0～S2抢占、现场保护和恢复门禁。
- `RoleRouting.md`：工作窗口职责、优先使用的Agent职责／SKILL和项目级专项策划路由。
- `WindowAutomation.md`：固定窗口注册、制作人自动派发、状态监控和失效降级规则。
- `GitIntegration.md`：专业窗口到专门Git集成窗口的请求、复核、提交、退回和异常升级合同。
- `../3DArtProductionWorkflow.md`：所有3D资产在Blender／AI 3D建模前必须遵守的批次清单、轴测图、
  三视图／简化说明、逐资产路线审批和返修回退门禁。
- `WindowRegistry.example.json`：本机窗口注册表结构示例；实际注册表写入被Git忽略的
  `.ai/dispatch/window-registry.local.json`。
- `Active/<派发ID>.md`：OpenSpec建立前的独立方案探索派发单。派发ID优先使用预定的
  OpenSpec change ID，并遵守批次号、并行领域和任务编号命名规范。
- 专业窗口完成方案讨论、用户确认决策摘要并创建OpenSpec后，派发单移动到
  `openspec/changes/<change-id>/dispatch.md`，随后与该OpenSpec一起归档；本目录不再建立
  独立历史副本。

## 协作状态

| 状态 | 含义 |
|---|---|
| 待领取 | 制作人已生成派发单，尚未交给专业窗口 |
| 方案讨论 | 专业窗口正在检查项目并与用户收敛实现或生产方案 |
| 等待复核 | 仅在存在跨职能依赖、公共合同或用户要求时等待对应窗口／制作人复核 |
| 可实施 | 决策摘要与OpenSpec已确认，所需文件和工具占用已授予 |
| 实施中 | 专业窗口正在开发、制作或执行专业验证 |
| 待验收 | 专业窗口已提交结果，等待测试、制作人或用户验收 |
| 暂停 | 因依赖、设计冲突、文件冲突或工具占用而停止推进 |

这些状态只描述窗口协作阶段。任务表中的状态、实际工时和备注始终由用户本人维护。

## 自治、锁与占用规则

- 派发单中的任务、可写路径、冻结方案和验收标准共同构成专业窗口的日常自治边界。在该边界内，
  窗口自主讨论、实施、验证、增量归档和准备提交，不等待制作人逐段批准。
- 用户在专业窗口作出的职责内决定立即生效；提问窗口负责记录，并直接通知受影响窗口。
  影响面不明、点对点协调失败或需要改变公共合同才升级制作人。

- 写权限以业务目录锁为主；场景、Prefab、ProjectSettings、共享配置、`.blend`和其他
  高冲突资产按单文件补充锁定。不得为了省事锁定整个项目，也不得要求逐个登记普通文件。
- 同一目录或高冲突文件在同一时段只能由一个实施窗口写入。只读检查不取得写锁，但
  任何会驱动Unity状态的读取、测试或截图仍须取得对应Unity实例锁。
- Unity、Blender文件和外部绘图工程保持工具独占。客户端、测试、主美和2D窗口按需点对点
  请求、核验和交接，不需要制作人逐次批准；争抢、失联或破坏性风险才升级。
- 多窗口共享同一Git工作区时，只有`AutoEra｜Git集成`窗口可以暂存和提交。专业窗口不得
  暂存、提交、变基、合并、切换分支或重写历史，只能按`GitIntegration.md`提交精确请求。
- Git集成窗口禁止`git add -A`和`git add .`，必须显式暂存请求路径，并在提交前确认暂存区
  没有其他窗口或用户内容。
- 所有窗口的Git提交标题、概要和正文描述必须使用中文；专业术语、文件名、类型名和派发／
  OpenSpec编号可保留原文。不得为满足本规则改写历史提交。
- 专业窗口不得直接修改`ActiveAssignments.md`，但必须自行维护所属派发单或OpenSpec中的
  决策、实施和验证记录。普通记录通过Git集成窗口提交，不请求制作人代写。

## 基本流程

1. 制作人只读核对任务表、设计来源、依赖、阶段门和可并行条件。
2. 制作人生成方案探索派发单并登记到`ActiveAssignments.md`。
3. 制作人优先按`WindowAutomation.md`向已注册专业窗口自动发送派发消息；窗口未注册、
   失效或派发失败时，降级为由用户手动打开对应窗口并发送派发单路径。
4. 专业窗口先检查项目、工具、SKILL和工作流。工作窗口可使用当前环境提供的全部SKILL，
   但应优先使用`RoleRouting.md`列出的职能能力；真正委派的子Agent仍遵守Agent白名单。
5. 专业窗口与用户直接讨论具体实现或生产方案，并按每累计两轮至少一次的规则自行增量归档。
6. 用户确认后，负责窗口自行创建和填写OpenSpec artifacts；影响其他职能时直接同步对应窗口。
7. 专业窗口在派发边界内自主实施和验证；Unity／DCC由相关窗口点对点交接。
   3D资产必须额外遵守`../3DArtProductionWorkflow.md`，前置出图和用户路线审批未完成时不得驱动
   Blender或AI 3D建模工具。
8. 每个独立工作单元完成后，专业窗口向Git集成窗口发送精确提交请求；合格即提交，只提交不推送。
9. 普通进度、单项决定、测试通过、归档和提交不通知制作人；异常按强制升级清单处理。
10. 测试窗口默认只诊断和报告，缺陷直接交回原实现窗口修复。
11. 整个派发批次完成后，负责窗口向制作人提交一次批次报告；制作人组织验收、OpenSpec归档和
   任务表手动更新建议。

## 制作人强制升级事件

- 任务范围、优先级、负责人或排期需要变化；
- OpenSpec任务映射、编号、批次边界或依赖需要变化；
- 跨窗口点对点沟通后仍无法解决的合同、路径或交付冲突；
- Unity／DCC失联占用、目标项目异常或存在破坏性操作风险；
- 验收标准冲突，或一个职能将破坏另一职能已冻结合同；
- 需要新的用户授权、任务表修改建议或框架核心边界调整；
- Git集成窗口发现路径越界、只读文件混入、归属不明或仓库异常；
- S0～S1暂停事件，或整个派发批次完成并进入验收。

除上述事件外，不向制作人发送“仅供知悉”的消息。
