## Context

本变更覆盖任务表 `ART-001`、`ART-002`、`ART-003`。主工程与 `ArtResource` 均使用 Unity 2022.3.62f3c1、URP 14.0.12，但主工程包含 GF_X、FSR、HybridCLR 等产品开发依赖，美术项目保持面向资源制作与预览的较小依赖集合。两个项目已经通过不同 Unity Skills 端口打开，本变更必须保持两者职责隔离。

当前已确认的产品方向是明亮风格化中模、简化 PBR、模块化资产与共享材质；第一版场景采用固定玩法骨架与编辑器生成视觉环境的混合路线。机器将使用程序化刚性关节动作，因此模型从 Blockout 起就必须满足可动部件和接口约束。正式批量资源生产尚未开始，现在建立基线的返工成本最低。

任务表是用户维护的只读执行台账。本变更可以输出建议状态与验收证据，但不得写回任务表。

## Goals / Non-Goals

**Goals:**

- 让 `ArtResource` 能够独立完成制作、预览、评审和版本化交付。
- 建立一个可重复验证的最小资源往返流程，提前发现比例、材质、锚点、GUID 与引用漂移。
- 在受控 LookDev 条件下比较三组完整视觉候选，并形成单一正式视觉基线。
- 用代表性样片验证并细化固定玩法骨架与编辑器程序生成视觉环境的混合场景路线。
- 把机器程序化动作所需的资源接口前置到 Blockout，而不在本变更实现动作运行时。
- 为后续 Art Bible、`P0-014`～`P0-016` 和正式资源生产提供可审计的输入与验收证据。

**Non-Goals:**

- 不批量制作第一版正式环境、机器、建筑、UI、VFX 或声音资源。
- 不实现 Motion Core、Motion Editor、AutoEra Adapter 或可视化动作节点编辑器。
- 不实现动物、动物动作、运行时随机地图、无限区块或存档地图种子。
- 不确定未经样片 Profile 的最终实例密度、材质预算、LOD 距离或毫秒预算。
- 不设计量产阶段的长期跨项目同步系统；本批只验证最小 `.unitypackage` 合同。
- 不修改 GF_X、`Assets/Game/ScriptsBuiltin/`、asmdef、HybridCLR 或 FSR 配置。

## Decisions

### 1. `ArtResource` 是唯一美术源权威

可编辑 DCC 源、Unity 制作资产、LookDev 场景和导出前 Prefab 均以 `ArtResource` 为准。主工程只保存经交付合同导入的资源及产品绑定，不在主工程直接修订源美术。发现问题时在美术项目修复并重新导出。

选择该方案是为了避免双向修改和 GUID 分叉。替代方案是两个项目都可编辑同一资源，但它无法可靠判定哪个版本具有权威性。

### 2. 使用书面合同加最小往返包验证边界

ART-001 先建立包含尺度、坐标、前向、Pivot、命名、材质、贴图、Prefab、Socket、作业点、VFX 点、状态灯点和程序化动作关节元数据的交付合同。随后只制作足以覆盖这些接口的最小样例包，在主工程完成导入、重复导入和引用检查。

本批使用 `.unitypackage`，保留并验证 `.meta` 与 GUID；工具包和美术资源包分开。主工程专属业务组件不得反向进入美术包。相比立即建设自动同步或共享 Package，本方案成本更低，也能先验证真实接口。

### 3. 三组候选必须在统一 LookDev 条件下完整比较

三组候选不是三张独立概念图，而是三个覆盖环境、机器、建筑、色彩、材质、灯光和俯视可读性的完整小型视觉系统。所有候选使用同一相机、光照、后处理、尺度参照、对象清单和截图视角。

评审矩阵至少比较风格契合度、俯视可读性、机器功能可读性、状态色冲突、制作成本、模块复用、程序化动作适配和场景性能风险。最终可以选择单一候选，也可以记录来源后融合，但必须只产生一套正式基线。

### 4. 场景路线以混合方案为目标，比较用于验证而非重新开放范围

基地、道路、农田、资源点、主要通道和可建造空间属于人工固定玩法骨架。地表分区、材质过渡、植被群落、碎石及非交互装饰由 Editor 工具生成；生成结果烘焙为可保存、可人工修整的确定场景。

ART-003 在同一测试区对 Terrain、模块化、手工布景和混合方式做轻量对照，用于确认混合路线中的具体职责、资产清单和风险。只有触发已记录的重新评估条件时才更换总体路线。

### 5. 玩法对象与视觉实例严格分离

资源点、建筑和机器仍是少量具有稳定身份的玩法对象；植被、矿床碎块、草地和碎石可以大量实例化，但不得逐个成为玩法实体。视觉生成不得改变玩法骨架、导航权威、碰撞权威或存档身份。

### 6. 机器从 Blockout 起满足程序化动作合同

代表性机器使用独立刚性部件、正确局部轴与 Pivot、稳定关节 ID、关节范围、默认姿态、Socket、作业点、VFX 点和安全收回姿态。逻辑根、导航和主碰撞不随视觉关节运动。

本变更只验证资源结构和交付完整性。动作求解、状态适配和性能 LOD 由 `P0-014`～`P0-016` 的程序变更实现，避免在美术项目复制玩法代码。

### 7. 性能使用证据门而非预设硬数字

样片记录代表性相机下的对象数、Renderer／材质情况、批处理或实例化条件、CPU／GPU 帧时间和明显瓶颈。ART-003 必须产出可比较的 Profile 证据，但最终环境密度、材质预算与 LOD 参数等待样片结果后确定。

## Risks / Trade-offs

- [两个项目依赖不同导致表现漂移] → 固定 Unity 与 URP 版本，记录必要渲染设置；最小包在主工程做最终外观验证，不把主工程全部依赖复制到美术项目。
- [三组候选范围过大] → 使用同一小型对象清单和相同镜头，只追求足以比较的完成度，不提前生产正式资产全集。
- [融合候选后失去一致性] → 每项融合必须记录来源与统一规则，最终只允许一套色彩、材质和轮廓基线进入 Art Bible。
- [程序生成破坏手工构图或玩法空间] → 生成器只拥有视觉区域，输出必须可烘焙、可局部重生成和可人工覆盖；玩法骨架不参与随机修改。
- [`.unitypackage` 人工流程易漏项] → 使用导出清单、版本元数据、干净导入检查和重复导入检查；长期同步机制留到合同稳定后决定。
- [机器动作接口限制造型] → 在低成本 Blockout 阶段验证关节和安全姿态；若造型冲突，在中模细化前调整，不在成品阶段切件补救。
- [没有预设性能硬预算导致验收模糊] → 本批验收“证据完整且无明显阻塞”，并把测得数据作为后续预算决策输入；不以主观流畅替代 Profile。

## Migration Plan

1. 记录两个项目当前 Unity、URP 和必要导入环境，建立 ART-001 合同与检查清单。
2. 在 `ArtResource` 建立受控 LookDev 与最小样例资源，完成首次和重复导入验证。
3. 在同一 LookDev 条件下制作三组候选并完成统一评审，冻结一套视觉基线。
4. 使用冻结基线制作代表性场景对照与混合方案样片，记录资产清单和性能证据。
5. 通过联合评审后，把合同、视觉基线和场景结论交给后续 Art Bible、动作工具和正式资源批次。

如果往返合同失败，回滚只删除主工程中的试验性导入包和绑定，权威源仍保留在 `ArtResource`；不得通过直接修改主工程副本掩盖问题。任何删除操作在实施阶段先解析并确认精确试验路径。

## Open Questions

- 最终环境密度、材质数量、LOD 距离和性能毫秒预算等待 ART-003 样片 Profile 后决定。
- `.unitypackage` 之后是否迁移到本地 UPM 包、自动导出或其它长期同步方案，等待代表性贯通和正式生产规模验证后决定。
