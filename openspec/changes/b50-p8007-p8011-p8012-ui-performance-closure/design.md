# B50 UI加载、性能与证据收口

## Context

当前40个UI预制体合计5253个GameObject，现场详情与操作弹窗体量大。需要以真实测量指导按需加载和刷新优化，并统一本次1920×1080验收与结构适配要求，清理代码/接线/验收状态混用的证据说明。

原始任务：P8-007、P8-011、P8-012。用户在2026-10-08确认全量详细规划及“复用现有架构、必要时局部重构”，随后确认本批方向；UI运行验收仅1920×1080，但Prefab结构仍考虑适配。当前仅规划，未实施。

## Goals / Non-Goals

**Goals:**

- 按基准识别大页热点，继续使用独立子Form、GF列表池和按修订刷新。
- 以1920×1080为唯一运行验收分辨率；结构门检查锚点、拉伸、缩放来源与布局冲突。
- 执行10/50/100台机器性能基准、50台60分钟稳定性和反复UI开关，建立可追溯证据与状态索引。

**Non-Goals:** 不机械拆每个装饰节点、不新增多分辨率验收、不全面换UI框架/美术风格；不顺手实现所有未接入页面或宣称G8完成，不修改任务表/共享Git索引。

实现边界见proposal.md的路径清单。新增产品类型只能进入AutoEra目录并使用AutoEra.*命名空间；本批不修改ScriptsBuiltin、asmdef、HybridCLR/FSR设置或用户任务表。场景/Prefab共享文件在实施前核对占用和精确清单，不按目录通配批量改写。

## Decisions

### 路线与取舍

| 候选 | 优点 | 代价 | 选择 |
|---|---|---|---|
| 复用既有服务并局部修正边界 | 保留既有规则与验证投入，可独立回归 | 需处理旧入口兼容 | 采用，符合用户A |
| 统一底座后重写接入 | 全局模式整齐 | 回归面与前期投入更大 | 不采用 |
| 只补调用，不调整责任 | 局部代码少 | 生命周期/状态风险可能残留 | 不作为本批方案 |

### D1 测量先于拆分

首先在同一Development Player记录FieldHudDetailForm、OperationDialogForm、ProgressReportForm、BaseCommandHubForm、SettingsForm首次/重复打开成本、布局重建、活跃对象与内存；仅拆具备独立交互/生命周期或明确热点的页面。目录写范围虽宽，每个执行单元先列精确契约/Prefab/C#清单，避免并发覆盖。

### D2 生命周期与异步

子Form沿用AutoEraUiNavigator与会话参数，父关闭增加请求版本/取消并回收迟到结果。用自有订阅令牌或对称退订管理读模型，关闭不销毁世界服务。列表沿用SpawnItem/UnspawnItem，只有证实大列表有问题才增加可见行复用，不替代已有对象池。

### D3 刷新与输入

对领域修订、选中与页面可见性做增量刷新，禁止无变化Update反复ToArray/格式化文本/重建布局。打开/关闭/取消/错误返回后世界输入阻塞由当前存活Form聚合，保持已有选择焦点与Esc语义；UI打开不暂停世界。

### D4 适配结构合同

运行视觉只检查1920×1080，不开展其他分辨率测试。根Stretch/零offset，GF根Canvas统一CanvasScaler；窗口/HUD按语义锚定，内部拉伸区与固定按钮区边界清晰，LayoutElement与父LayoutGroup尺寸责任明确，不混用脚本绝对坐标争夺同轴。字体、列表行长与动态状态用容器约束处理。

### D5 性能门与基准冻结

固定硬件、构建、场景种子和采样设置，测10/50/100台正常/缺电/恢复。50台60分钟，每个阶段记录p50/p95/p99、GC Alloc、UI打开延迟、内存/队列/订阅数量；预热后无状态变化的常驻刷新不持续分配。先测基准再按实测冻结有依据的绝对预算，不以未测毫秒数承诺帧率。重复开关100次，回到同等状态后存活Form/订阅/队列不随次数增长。

### D6 证据与状态

建立功能→权威来源→代码入口→正式运行测试→玩家操作→验收证据索引。历史通过保留原时间与版本，过期交接说明标注被何证据替代；代码存在不代表接线或验收完成。只提出任务表状态调整建议，不写工作簿。

## Risks / Trade-offs

- **拆页导致异步迟到重新打开窗口** → 版本令牌/取消测试覆盖快速开关和换世界；不能只断言关闭时无异常。
- **提高FPS牺牲业务步或UI反馈** → 同场景并测功能和结果，优化不得降低采样/事件规则或隐藏必要反馈。
- **性能门无法在当前硬件跑测** → 文档与静态检查可交付，但Player性能状态保持未执行，不能用编辑器截图替代。
- **本次尚无新运行证据** → 本文件定义将来的验证门；历史测试保留时间/版本，不当作本次复跑。

## Migration Plan

1. 取得实施授权、核对原始任务和依赖证据；读取conventions，记录实际修改文件及共享工具占用。
2. 先补能暴露问题的测试和基准，再按tasks.md实施领域/接入/表现单元；结构与序列化变更停止Play Mode，使用普通Unity编译。
3. 按规格逐场景验证，保存原生XML、日志和必要1920×1080截图/Player基准；UI截图不代替业务结果断言。
4. 回滚策略：每次迁移同时版本化契约、生成字段、Prefab与手写生命周期逻辑；保留UIViews/请求协议兼容。性能回归按单页回退，不能重置业务状态消除问题。
5. 更新本变更evidence索引与未覆盖项；仅当实际完成后勾选任务。阶段验收与用户任务表状态另行处理，不自动Git提交或归档既有变更。

## Verification

- 每条spec Scenario至少对应一个可执行测试或明确人工证据步骤，映射表随实施写入本变更evidence。
