- [x] 1.1 新增 `AutoEraComponentPickRequest`：**目标槽位**（机器身份 ＋ 硬件类别 ＋ 槽位序号）
      ＋ 结果写回处（`AutoEraUiSelectionRequest`，本工程「界面把结果交回调用方」的既定做法）。
      它刻意不描述「挑哪一件」——那是玩家在页面里做的决定。
      调用方不传结果对象时会自己建一个：这样「有没有人来读结果」与「结果能不能写」是两件事。
      （**踩到过**：第一版没做这个兜底，`MachineLibraryForm` 不传结果，于是确认时结果被静默丢掉；

- [x] 1.2 `UiComponentCandidate`：一件散件 ＋ 它对这个槽位是否兼容。
      **兼容判据只有「硬件类别与槽位类别一致」一条**，其余不可安装因素（可用性等）照原样展示——
      界面不自己定第二套「什么时候能装」的规则，那是领域 `HardwareGate` 的职责。
      不兼容的候选**依然列出、依然可预选**，只是不能确认并给出具体原因（「它是执行器，而本槽位是核心」）。
- [x] 1.3 新增 `ComponentPickerReadModel.cs`：`ComponentPickerSnapshot`（目标槽位／当前安装／候选／
      预选／比较行／确认被拦下的原因）＋ `IComponentPickerReadModel`（`Snapshot`／`Changed`／
      `Select`／`ClearSelection`）。
      真实实现**组合** `IComponentReadModel`，不自己再扫一遍花名册：「哪些组件算散件」
      「型号叫什么名字」都已经有一处实现，复制一份迟早出现两种口径（上一批刚踩过这个坑）。
      槽位里那件组件的显示名也取组件域读模型**已安装**那一列的行，与组件库页看到的是同一个名字。

      不是孤零零一个增量：只写「+3」回答不了「装完还剩多少容量」，而那正是玩家要判断的事。

## 7. 一条反复出现的判据错误（第三次，值得单独留痕）

`ComponentPickerForm` 原本被 `ui-game-system-integration` 的 2.7 列为「领域未接入」，
理由写的是「组件域尚未接入运行路径：候选组件没有数据来源」。但组件域在
`component-domain-readonly-wiring` 那一批就已经接线：目录表与花名册**两半都在生产里**，
`ComponentReadModel` 的散件一列一直在用它们。这一页缺的只是「散件 → 候选」这一层投影。

前两次误判是 `ComponentLibraryForm`（2026-09-21）与 `SettingsForm`（2026-09-21），
三次的错误形态完全一样：**把「还没有这一页的读模型」当成了「这个域没有后端」**。

因此本批把这条经验写成执行纪律（已记入 2.7）：**在给任何界面写「未接入」之前先做代码侦察**——
判据是「该界面依赖的领域服务在生产里没有创建者」，而不是「这一页还没人写读模型」。
