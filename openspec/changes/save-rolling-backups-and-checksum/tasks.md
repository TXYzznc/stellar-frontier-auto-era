# 任务

## 1. 数据格式：校验值、槽位ID、保存时间、长度

- [x] 1.1 `SaveSlotRecord` 增加 `SlotIndex`、`SavedUtcTicks`、`ContentLength`、`Checksum`、
      `OfflineSettlementPending`；`CurrentVersion` 升到 2，并记录 `FirstChecksumVersion = 2`。
- [x] 1.2 新增 `SaveChecksum`：SHA-256 小写十六进制，按**显式规范化载荷**计算。
      **刻意不哈希序列化后的 JSON**——字段顺序/缩进/转义随序列化器实现变化，
      那样算出来的校验值会在一次无害的重序列化之后全部失效，把「换个写法」误报成「存档损坏」。
- [x] 1.3 校验字段就是规格列出的那一组（版本、槽位ID、保存UTC时间、世界时间、摘要、内容长度、内容），
      任一处被改动都能判定出来；比较用恒定时间实现。
- [x] 1.4 **旧格式仍能读**：`Version < 2` 的记录没有校验值，按迁移入口接受。
      一次格式升级不该把玩家所有旧存档判成损坏。

## 2. 服务：三份滚动备份

- [x] 2.1 `BackupCount = 3`，路径 `slot_n.json.bak1|bak2|bak3`（**1 最新**）；
      `GetSlotPath` / `GetBackupPath` 公开给测试与工具。
- [x] 2.2 写入顺序按规格：序列化 → 写临时文件 → **校验临时文件** → 轮转备份 → 原子替换。
      校验在替换之前，所以写坏的临时文件永远不会变成正式存档。
- [x] 2.3 滚动规则 `bak2→bak3`、`bak1→bak2`（丢弃 bak3），被替换下来的正式存档成为新的 `bak1`；
      第一次保存不产生备份（没有「被替换下来的旧内容」）。
- [x] 2.4 `Read`：正式存档 → 三份备份由新到旧；逐份校验（可解析、版本不高于当前、
      `SlotIndex` 与文件名一致、版本 2 起长度与校验值都对）。
      正式存档不存在但有可用备份时是**可恢复**而不是「空槽位」；
      版本过新是确定结论，不允许被备份盖过去。
- [x] 2.5 **不静默回退**：用备份时返回独立状态 `RecoveredFromBackup` 并带 `BackupIndex`；
      `IsSuccess` 涵盖它（「有没有内容」），`IsPrimary` 只对正式存档为真（「有没有回退」）。
- [x] 2.6 `Delete` 删主文件、临时文件与三份备份；`HasBackup`（存在）与 `HasUsableBackup`
      （可读且通过校验）分开——后者才是「恢复」能不能点的判据。
- [x] 2.7 `ListBackups(slot)` 逐份给出存在／可用／时间；`RestoreFromBackup` 提升
      **最新一份可用**备份，删掉比它新的备份（按定义都不可用）、比它旧的依次前移，
      于是「序号 1 最新」与「链上都是可用内容」同时成立。
- [x] 2.8 构造函数增加可注入的 UTC 时钟（默认 `DateTime.UtcNow`），便于断言保存时间；
      写入 API 增加 `offlineSettlementPending` 重载（旧签名保持不变）。

## 6. 一条流程观察

这一批是「任务名里已经写了的东西，实现里其实只做了一半」。
判断方式很直接：把任务的那句话逐个名词拆开，对着实现数一遍——
「原子写入、**校验**与**三份滚动备份**」三个名词里，前一个是真做完的，后两个没有。
比起重新翻一遍设计，这种「拿任务名当清单」的做法更快也更不容易漏。
