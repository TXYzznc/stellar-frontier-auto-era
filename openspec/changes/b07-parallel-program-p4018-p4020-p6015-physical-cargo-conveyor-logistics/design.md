## Context

当前第一版使用抽象“物品单位”、缓存与逐单位原子转移，明确不从场景对象推导资源数量。b06 已建立程序化机构与动作原型，但其传送带只负责表现验证，不拥有产品物流权威。用户随后确认货物应具有真实物理表现、传送带应成为玩家可建造的克制物流对象，并确认三段输送、被动出料队列、下游主动拉取与唯一归属链。

该变更跨越资源缓存、机械臂放置、Unity 物理、传送带实体、仓库接收、存档和离线推进。实现必须位于 `Assets/Game/Scripts/AutoEra/`，不得将产品逻辑写入 `ScriptsBuiltin` 或独立 Motion Core 包。

## Goals / Non-Goals

**Goals:**

- 保持资源数量与结算数据权威，同时提供可碰撞、可落下、可抓取的货物代理。
- 保证一批货物在任意时刻只有一个逻辑拥有者，所有交接可追溯、可恢复且不复制。
- 支持玩家建造三段式传送带，并让下游对象主动从出料口拉取货物。
- 让在线物理表现、存档恢复与离线结算得到相同的资源守恒结果。
- 通过窄适配层复用 b06 的 MotionGraph 表现，不让动作图成为库存或物流权威。

**Non-Goals:**

- 不实现分拣器、合流器、复杂路由图、管线网络、物流吞吐优化面板或以传送带布局为核心的独立玩法。
- 不以重量、体积、模型数量或刚体碰撞结果计算库存容量、配方消耗和经济结算。
- 不使用带面摩擦推动刚体，不逐帧物理模拟离线时间。
- 不在本变更中重做 b06 的通用动作图运行时、导航、建造系统、完整仓库系统或正式美术资源。

## Decisions

### 1. 数值权威与物理代理分层

权威层使用 `CargoLot` 表达资源类型、单位数量、唯一 ID、当前拥有者、所有权版本和状态；表现层使用可池化的 `PhysicalCargoProxy`。一个代理可代表多个单位，代理销毁、隐藏或 LOD 合并不改变 `CargoLot` 数量。

选择分层而不是“一刚体一单位”，因为后者会把性能、碰撞稳定性和场景可见数量错误地变成经济权威。资源类型配置可提供模型、碰撞体、质量、摩擦、弹性、每代理默认单位数和最大可见代理数，但容量仍使用现有抽象单位。

### 2. 使用显式所有权事务

所有权类型固定为世界自由态、机械臂抓握端、传送带运输段、出料口、接收对象。转移通过单一事务入口完成：验证来源与版本、预留目标、提交新拥有者、发布事件；失败时维持最后一个已确认拥有者。

不允许用复制场景对象、先删后加两个独立操作或碰撞回调直接改库存完成交接。幂等事务 ID 用于抵抗重复回调、读档重放和离线恢复。

### 3. 物理模式由所有权派生

- 世界自由态：Rigidbody 动态模拟，可碰撞和自然落下。
- 机械臂抓握端：代理设为受控状态并跟随抓握锚点。
- 接料段、主带、出料段：代理由工业运输约束沿参数化轨迹推进，保留可配置碰撞表现，但不依赖摩擦驱动。
- 出料口：正常暂存位使用受控摆放；超出可见暂存位的代理可释放为自由物理表现，但逻辑拥有者仍是出料口。
- 接收对象：由接收对象决定隐藏、存储表现或后续转移。

模式切换只在所有权事务提交后发生，避免画面先动而权威失败。

### 4. 传送带是可建造实体，但保持三段固定能力

传送带实体由接料短滚筒、主带和出料短滚筒组成。每段有稳定锚点、轨迹、速度、容量／间距、占用和动作状态。对象目标放置到传送带时优先使用接料能力；坐标目标进入接料范围时可自动捕获。

传送带只将货物送入自己的出料口，不保存下游目标、不主动推送、不根据下游容量倒逼主带。这样既满足玩家建造与组合，又避免形成复杂产线路由系统。

### 5. 出料口是被动、逻辑不拒收的队列

出料口在权威层维护有序 `CargoLot` 队列，不因正常显示位不足拒绝来自本传送带的货物。表现层使用有限暂存位和代理上限表达堆积；多余货物可以形成可见溢出，但仍归出料口。

该规则避免主带因画面容量产生数值死锁。需要设置诊断阈值与代理上限，防止无限刚体堆积；超过表现预算时合并或隐藏代理，但保留权威数量和告警。

### 6. 下游以拉取请求竞争出料口

下游传送带、仓库或接收设备保存对上游出料口的关联，并在自身可接收时发出带优先级、请求序号和幂等 ID 的拉取请求。出料口按优先级降序、同优先级请求序号 FIFO 选择一个接收方并执行所有权事务。

上游不保存下游路由，也不广播推送。关联失效、目标满载或请求取消只移除对应拉取请求，不改变队列货物所有权。

### 7. 存档保存权威状态，离线推进使用离散事件

存档保存 `CargoLot`、拥有者引用、所有权版本、传送段进度、出料队列顺序、下游关联、请求优先级与序号。世界自由态和可见溢出代理额外保存必要的量化姿态／速度，以恢复近似画面；库存守恒不依赖这些表现字段。

离线推进只处理运输到达、入队、拉取申请、仲裁和接收提交等离散事件。恢复在线后根据权威状态重建代理，不回放离线刚体。

### 8. 分阶段实施并设置容量门

先实现纯 C# 所有权与队列核心，再实现传送带状态机和代理模式切换，最后接入存档、离线与可视验证。代表场景必须验证大量出料积压时的代理数量、主线程物理成本和零高频 GC；正式预算由实测后冻结，不在提案阶段拍脑袋写死。

## Risks / Trade-offs

- [物理代理与权威状态脱节] → 所有模式切换只响应已提交事务；提供一致性诊断和强制重建入口。
- [出料口逻辑无限接收造成视觉／内存膨胀] → 权威队列可增长，但代理池、可见暂存位和溢出代理有独立上限，并产生可合并告警。
- [多下游竞争产生重复提取] → 单线程仲裁、版本检查、幂等事务 ID 和同刻稳定排序共同保证唯一提交。
- [可建造传送带挤占机器物流核心] → 第一版只提供固定三段能力和简单关联，不提供复杂分流、合流与产线优化系统。
- [离线结果与在线物理画面不同] → 只要求资源、归属、队列和进度一致；恢复时允许重建近似稳定摆放，不承诺逐刚体轨迹一致。
- [Unity 物理与对象池生命周期复杂] → 将物理代理适配限制在主线程表现层，权威核心保持纯 C#、可确定性测试。

## Migration Plan

1. 先修订正式设计基线并新增取代 DEC-149 局部内容的决策记录。
2. 用户手动在任务表新增 `P4-018`～`P4-020` 与 `P6-015`；本 OpenSpec 名称与四项任务保持对应，避免阶段4反向依赖阶段6施工系统。
3. 新增纯数据合同和守恒测试，不改变现有缓存／资源转移调用方。
4. 以适配器接入机械臂、三段传送带和接收对象，保留旧抽象转移作为未迁移对象的兼容路径。
5. 接入存档和离线推进后执行在线／离线对照回归。
6. 在代表场景通过性能门和可视验收后，才允许第一版内容使用可建造传送带。
7. 回滚时禁用传送带建造入口并迁移其队列货物至最近合法缓存；不删除 `CargoLot` 权威记录。
