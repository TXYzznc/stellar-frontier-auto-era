## Decisions

1. 先配置和纯业务，再接场景。复用永久ID/注册表/时间/现有Procedure和GF Entity；机器服务不持有Prefab节点，UI仅投影状态和提交管理意图。复用现有类型优先于新造通用管理器。
2. P0-011建立第一版目录覆盖与逻辑配置；仅登记真实可解析的资源引用。待美术资源与不适用引用分开建模并明确错误/禁用状态，禁止伪造有效路径。缺资源不能宣称全目录可实例化；任务表整项DoD保留至全部覆盖。
3. 配置走已验安全JSON→校验→事务生成工具；不手改xlsx/生成C#。首次执行先盘点ID、已有表、准确文件及变更集合，确保不覆盖现有Core和Foundation。
4. 名称/组件归属/容器为机器业务权威。货舱是容量效应器，占效应器槽；不是第四类槽，也不是独立库存。配置结构可还原验证，但不顺手实现完整存档系统。
5. 五档优先级、同级FIFO、容量、安全中断和算力成本沿现有规则；B10作业点等待队列不冒充机器任务队列。外部供电/信号以明确接口和测试适配输入，本批不重建电网。
6. 2D与客户端先点对点冻结公开字段/管理命令/拒绝原因。美术设计经制作人结构功能报告→用户视觉决定，随后自行连续切图/装配；业务接入无需再次逐步放行，界面未通过不伪造完成。通用样式和无新增资源条件直接复用。
7. 专业负责人按RapidExecution六门槛拆冻结的机械子包，保留复核责任；当前OpenSpec/视觉判断不拆给快速执行。

## Risks / Trade-offs

- 配置膨胀或过时规则 → 按现行来源逐行映射，缺省不造玩法。
- 共享正式UI覆盖 → 美术仅ArtResource独立候选，客户端负责主工程受控接入及GUID依赖检查。
- 硬件更新破坏动作 → 模型/合同只读复用，换装只处理对应视觉挂点，无机械插拔动画。
- 数据并发 → 使用既有指纹/事务，不恢复旧任务表，不强制覆盖用户改动。
- 未完成能源/算法阻塞 → 业务边界接口+明确测试输入，不给玩家添加手动作业按钮。

## Migration Plan

先留存精确文件/引用基线→增量数据服务与测试→独立机器集成用例→用户通过的UI候选接入→QA回归。回退仅本次新增/修改记录，不重置其它窗口现场，不删除既有正式模型/UI。事务修复既有成果只复用；若新框架缺陷须精确报制作人授权。
