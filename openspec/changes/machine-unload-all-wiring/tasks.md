# 任务

## 1. 领域：整台一起卸（原子的那个动作）

- [x] 1.1 `MachineInstance.RemoveAll(ManagementOrigin)`（internal）：
      来源**只接受整备环境（`Library`）**——规格把「一键卸下」列在「未部署机器处于整备环境」之下，
      已部署机器的硬件修改「必须现场逐项完成」；批量拆一台正在服役的机器不是这一版设计里的动作，
      所以如实拒绝（`InvalidOrigin`）而不是顺手放开。
- [x] 1.2 **原子性**：先算「全部卸下之后」的余量（只剩 `BaseCapacity`；算力与逻辑占用必须归零，
      含等待算力的计数），任一条不满足就整体拒绝、**一件都不动**；通过了再一次性清空。
      为什么不能在门禁之后逐件调 `Remove`：逐件会在中途失败并留下半卸状态，那正是「原子」要排除的结果。
- [x] 1.3 应用时清空每个槽位并把组件的 `OwnerId` 置为 `Invalid`——**「回库」在实现里就是清空归属**，
      组件因此重新成为组件库里的散件；不需要另一套库存系统。
- [x] 1.4 一件都没装时返回 `MissingComponent`（这个意图没有意义，如实拒绝而不是报成功）；
      未知机器返回 `InvalidState`；有进行中的行为时返回 `WaitingForSafeStop`。
- [x] 1.5 `MachineRoster.RemoveAll(machineId, origin)` 按 id 转发；
      新增 `MachineInstance.InstalledComponentCount`（界面与测试都要用它判断「有没有东西可卸」）。
- [x] 1.6 `MachineHardwareOperation.BeginRemoveAll(machineId, origin)`：与单槽拆卸走**同一条**协调器
      （同样的来源门禁、同样的等待安全停机、同样的请求版本取消），内部只多一个 `_removeAll` 标志。
      另起一条路径就会让「什么时候不能改硬件」出现第二份判断。

## 5. 一处过期的范围判断（顺手更正）

批次 9 之前的任务表备注把「一键卸下」与「升级／出售」并列成「经济域未接入」。侦察发现它
**根本不依赖经济域**：它只依赖机器域的槽位归属，而「回库」在实现里就是清空 `OwnerId`。
所以它是本批就能做的活，而不是等经济域的活。

这与 2.7 那条纪律的两次误判是**同一类错误的第三个方向**：前两次是「把还没写的读模型当成没有后端」，
第（五）次是「把设计明确不做的当成还没做」，这一次是「把不依赖某域的活挂到了那个域上」。
共同点都是**没有先侦察依赖关系就给出了缺口归属**。
